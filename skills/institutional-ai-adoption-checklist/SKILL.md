# institutional-ai-adoption-checklist

大学が組織として AI を導入・展開する時の論点を、委員会、執行部、部署運用に接続する。AI エージェントは、成熟度診断、チェックリスト、上程メモ、稟議・承認に向けた確認事項を返す。

## いつ使うか

- AI 検討委員会や情報政策会議の初回資料を作る時。
- 部署または全学の AI 利用ルール、契約、研修、監査を整理したい時。
- 執行部向けの 1 ページ要旨や論点表を作りたい時。
- 現在の導入成熟度を自己診断し、次の半年の優先順位を決めたい時。

使わない場面:

- 個別資料を AI に入れてよいかだけを判断する時。`check-info-level` を使う。
- 個別業務の文案作成や学生対応。該当する業務別 skill を使う。
- 導入可否の最終決裁。執行部・委員会の判断が必要。

## 入力前の確認

個別資料や内部検討メモを読む前に、次を確認する。

- 検討単位: 全学、部局、部署、プロジェクト。
- 現状: 未検討、散発利用、試行、部分展開、全学展開。
- 利用目的: 事務効率化、教育、研究支援、学生対応、広報、IR など。
- 契約: 無料 Web、個人利用、法人契約、API、学内閉域。
- 情報分類: 学生、人事、入試、研究、内部会議資料を扱うか。
- 意思決定経路: 担当部署、委員会、執行部、理事会、教授会。

## 成熟度モデル

| 段階 | 状態 | 次にやること |
|---|---|---|
| 1. 未検討 | 公式見解や担当部署がない | 担当部署と検討体制を置く |
| 2. 散発利用 | 個々の職員・教員が試している | 入力前確認と禁止領域を先に定める |
| 3. 試行 | 特定部署で限定利用している | 契約、研修、ログ、問い合わせ経路を整える |
| 4. 部分展開 | ガイドラインや契約があるが対象限定 | 監査、評価、改善サイクルを作る |
| 5. 全学展開 | 一定条件下で組織利用している | 半期レビュー、教育研究への接続、リスク監査を行う |

## チェックリスト

| 領域 | 最初に整えること | 次に整えること |
|---|---|---|
| 方針 | 基本方針、禁止領域、入力前確認 | 改訂周期、問い合わせ窓口、例外申請 |
| 契約 | 学習利用、保存、削除、ログ | 認証、権限、監査、ベンダー管理 |
| 業務 | 高頻度・低リスク業務の洗い出し | 業務別 skill と運用記録 |
| 研修 | 職員向け基礎研修 | 部署別研修、管理職研修 |
| 評価 | 試行結果の記録 | 効果測定、事故報告、改善サイクル |

## 手順

1. 検討単位と成熟度を仮判定する。
2. 禁止領域と入力前確認の最小ルールを先に置く。
3. 契約、研修、監査、問い合わせ経路をチェックリストで整理する。
4. 委員会・執行部で決める論点と、担当部署で進めるタスクを分ける。
5. 1 ページ要旨、論点表、次の 90 日タスクを返す。

## 出力フォーマット

```markdown
## 成熟度診断
<1-5 と理由>

## 主要論点
1. <論点>
2. <論点>
3. <論点>

## 優先タスク
| 期限 | タスク | 担当 | 確認先 |
|---|---|---|---|

## 上程メモ骨子
- 背景:
- 現状:
- 判断が必要な事項:
- 想定コスト:
- リスク:
- 次の決定期限:

## 残リスク
- <未確認事項>
```

## 落とし穴

| 合理化 | 実態 |
|---|---|
| まず便利な使い方を広げればよい | 禁止領域と入力前確認がないと事故対応が後追いになる |
| ガイドラインを作れば導入完了 | 契約、研修、問い合わせ、監査、更新まで必要 |
| 全学契約すれば安全 | 契約だけでは権限、ログ、規程、教育研究上の責任は解決しない |
| 委員会で議論すれば進む | 決める論点、担当部署、期限を分けないと停滞する |
| AI 活用推進部署だけで決められる | 情報、法務、教務、学生支援、研究支援、広報との接続が必要 |
