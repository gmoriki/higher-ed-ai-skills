**更新日:** 2026-05-10

- [Agent Skills specification](https://agentskills.io/specification)

## 本ガイドが解く問題

`higher-ed-ai-skills` の `SKILL.md` は、大学職員が AI エージェントに大学業務を頼むための protocol である。AI 活用の一般論や人間向け読み物ではない。

同時に満たすこと:

1. `description` が大学職員の発話から skill を起動できる。
2. 本文が AI エージェントの実行手順として読める。
3. 本文やファイルを読む前の入力前トリアージを必要な場面で促す。
4. 出力が、判定、根拠、確認先、次アクション、残リスクに分かれる。
5. 所属大学の規程や決裁権者で上書きされる余地を残す。

## 廃止した考え方

`Reference type / Task type` の二分類は使わない。全 skill は unified protocol として書く。

違いがあるのは「何を返すか」と「副作用があるか」だけである。

| 型 | 例 | 書き方 |
|---|---|---|
| 判断型 | 入力可否、利用範囲、開示要否 | 判断軸、前提確認、出力フォーマットを明示 |
| 執行型 | 文案作成、分類、レビュー、議事録運用設計 | 手順、検証、成果物を明示 |
| 副作用あり | ファイル作成、外部送信、公開、権限変更 | `compatibility:`、`allowed-tools`、承認条件を明示 |

## frontmatter

基本形:

```yaml
---
name: <kebab-case>
description: >
  <ユーザー発話パターン、業務場面、返すもの、除外条件を 150-400 字程度で書く>
license: CC BY-SA 4.0
metadata:
  version: "<semver>"
  last_updated: "<YYYY-MM-DD>"
  author: gmoriki
---
```

必要な場合だけ追加する:

```yaml
compatibility: >
  Requires top-level Claude Code session with Task tool.
when_to_use: >
  description に収まらない追加 trigger。
argument-hint: "[text or file path]"
allowed-tools: Read Task Bash(file:*)
metadata:
  disable-model-invocation: true
```

`description` は機能説明ではなく trigger 設計として書く。

悪い例:

> 大学業務で生成 AI サービスを利用する際の機密情報取り扱い判断フレームワーク。

良い例:

> 大学職員が「この資料を AI に入れてよいか」「本文を読む前に入力可否を判断して」と相談した時に使う。資料種別、公開範囲、情報カテゴリ、処理目的、AI 実行環境を確認し、本文を読まない事前トリアージまたは内容確認後の Level 判定を返す。

````markdown

- <読んでよい条件、読まない条件>

## <中核節>

<判断軸、分類表、手順、チェックリスト、フロー>

## 出力フォーマット

```markdown
## 判定
...
```

## 落とし穴

| 合理化 | 実態 |
|---|---|
````

必須節:

- `いつ使うか`
- `入力前の確認`
- 中核節
- `出力フォーマット`
- `落とし穴`
- `関連`

## 入力前の確認

大学業務では、AI が本文を読むこと自体が問題になる場合がある。次に該当する skill は、本文処理の前に必ず入力前トリアージを持つ。

- 学生、受験生、教職員、研究参加者の個人情報を扱う。
- 成績、相談記録、入試、人事、懲戒、ハラスメント、障害配慮、メンタル不調を扱う。
- 未公開の議事録、稟議、予算、研究構想、契約条件を扱う。
- ファイル添付、OCR、メタデータ、コメント、トラックチェンジ、非表示シートを扱う。

書き方:

```markdown
本文やファイルを読む前に、資料種別、公開範囲、含まれそうな情報カテゴリ、
処理目的、利用予定の AI 環境を確認する。不明な場合は本文ではなく情報カテゴリで質問する。
```

## 出力フォーマット

業務別 skill は、少なくとも次を返す。

- 判定または結論
- 根拠
- 推奨対応
- 確認すべき規程・担当部署・決裁権者
- AI に渡してよい資料範囲
- 残リスク

例:

```markdown
## 判定
<可 / 条件付き / 不可 / 要人間確認>

## 根拠
- <業務文脈>
- <情報カテゴリ>
- <所属大学で確認すべき規程>

## 推奨対応
1. <次の行動>
2. <次の行動>

## 確認先
- <部署 / 委員会 / 決裁権者>

## 残リスク
- <未確認事項>
```

## 落とし穴

落とし穴は、AI と人間の合理化を止めるための節である。以下のような表で書く。

| 合理化 | 実態 |
|---|---|
| Enterprise 契約なら何でも入れてよい | 契約は学習利用を止めるだけで、法令、規程、権限、記録保存の問題は残る |
| 匿名化したつもりだから安全 | 属性の組合せ、固有表現、発言内容で再特定される |
| FAQ だから AI が自動回答してよい | 公開情報に基づく定型回答と、個別事情の判断は別物 |
| 検知ツールで AI 使用を断定できる | 検知結果は補助情報であり、処分や不正認定の単独根拠にはしない |

## 文体

- 断定的に短く書く。
- 「本スキルは〜を提供する」を多用しない。
- 「ユーザーが〜と聞いたら、AI は〜を確認し、〜を返す」と書く。
- 「所属大学の規程が優先」で終わらせず、確認する規程、確認先、決裁権者、記録に残す事項を書く。
- 「AI 可」「AI 完結可」は強すぎる。必要に応じて「公開情報に基づく定型下書き可」「個別判断は有人確認」と書く。

## references と examples

`SKILL.md` 本体は実行に必要な最小限へ絞る。長い背景説明、外部資料、詳細事例は `references/` または `examples/` に分ける。

- `examples/`: 想定相談と理想応答。
- `references/`: 根拠資料、詳細表、長いワークフロー。

本体から参照ファイルへは相対リンクで明示する。
